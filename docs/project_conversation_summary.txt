  AI LOG ANALYTICS PLATFORM — PROJECT CONVERSATION SUMMARY
  A plain-English walkthrough of everything we built together

Hey, let's talk through what we actually did here — not the technical jargon,
just a honest conversation about the journey from blank repo to a full banking
data platform.

--------------------------------------------------------------------------------
WHERE WE STARTED
--------------------------------------------------------------------------------

You came in with a clear goal: build an AI Log Analytics Platform. Not just
any platform — one that could handle the weight and sensitivity of a banking
environment. That's a very different ask from a generic log viewer. Banks deal
with regulations, audits, fraud, millions of transactions per hour, and zero
tolerance for data loss. So the architecture had to reflect that from day one.

We didn't write a single line of code first. Good instinct. We sat down and
designed the house before laying the bricks.

--------------------------------------------------------------------------------
THE ARCHITECTURE CONVERSATION
--------------------------------------------------------------------------------

The first thing we settled on was structure. We laid out a full project
blueprint — ingestion, pipeline, AI engine, storage, API, dashboard, alerting.
A clean separation of concerns so that one layer doesn't bleed into another.

Then you made a smart call: Azure Synapse Analytics for the storage layer,
with the Medallion Architecture — Bronze, Silver, and Gold. This is the right
pattern for a banking platform and here's why we chose it:

  Bronze  — "Don't touch the evidence."
            Raw logs land here exactly as they arrived. No transformation,
            no cleaning, no judgment. If something goes wrong downstream,
            you always have the original receipt.

  Silver  — "Make it trustworthy."
            This is where we clean, normalize, deduplicate, and conform the
            data. We attach surrogate keys, enforce types, validate amounts,
            and link records to proper dimensions. This layer is your single
            source of truth.

  Gold    — "Make it useful."
            Business-ready, AI-enriched, pre-aggregated, query-fast. This is
            what Power BI connects to, what analysts query, what the anomaly
            alerts are built on.

It's a sensible pattern. Each layer has a clear job and a clear owner.

--------------------------------------------------------------------------------
THE DATA MODEL CONVERSATION
--------------------------------------------------------------------------------

Then you pushed further — make it banking-specific. Not just generic logs.
Real banking domain entities. And you asked us not to hallucinate. Fair ask.

So we grounded every table in real banking operations:

  - Transaction logs    → What happened to money (TEMENOS, FLEXCUBE, FIS)
  - Authentication logs → Who tried to access what, from where
  - API gateway logs    → What called what, how long it took
  - Application errors  → What broke, where, in which service
  - Audit logs          → The compliance trail — who did what, when
  - Fraud alert logs    → What the fraud engine flagged and why

Every table maps to something a banker, a compliance officer, or a fraud
analyst would actually recognise. No invented concepts.

We applied Kimball dimensional modelling to the Gold layer — the star schema
pattern that has powered data warehouses for decades. Facts at the centre,
dimensions around the edges, foreign keys connecting them cleanly.

We also handled SCD2 — Slowly Changing Dimensions — for accounts and customers.
Because in banking, a customer's risk rating changes, an account gets frozen,
a product gets upgraded. You need to know not just what the data is today,
but what it was on the day a transaction happened. SCD2 gives you that.

Three Gold marts came out of this:

  Transaction Analytics Mart    — Follow the money
  Security & Auth Mart          — Follow the access
  Application Health Mart       — Follow the failures

Each one is a star schema. Clean, fast, auditable.

--------------------------------------------------------------------------------
THE DDL CONVERSATION
--------------------------------------------------------------------------------

Five migration scripts, written in proper Azure Synapse SQL:

  001 — Bronze external tables (Serverless SQL, pointing to ADLS Gen2)
  002 — Silver dimensions (SCD2, REPLICATE distribution, CCI)
  003 — Silver facts (HASH distribution, quarterly partitions, dedup)
  004 — Gold dimensions (flattened current snapshots, lineage columns)
  005 — Gold facts, aggregates, anomaly registry, embeddings store

A few deliberate decisions in the DDL worth noting:

  CLUSTERED COLUMNSTORE INDEX on every fact/aggregate table.
  Because banking analytics is columnar by nature — you're always
  aggregating across millions of rows on a handful of columns.

  REPLICATE distribution on small dimension tables.
  HASH distribution on large fact tables, keyed on account_sk or
  transaction_ref — the most selective join column in banking queries.

  Quarterly RANGE RIGHT partitions on facts.
  Banks run quarterly reports. Regulators ask for quarterly data.
  Partitioning by quarter makes those queries orders of magnitude faster
  and makes archival straightforward.

  PII masking by design.
  Account numbers are masked (last 4 only), email is domain-only,
  postcode is prefix-only. Compliance isn't bolted on — it's in the schema.

--------------------------------------------------------------------------------
THE SPARK NOTEBOOKS CONVERSATION
--------------------------------------------------------------------------------

Five PySpark notebooks to move data through the layers:

  brz_ingest_logs                — Reads from Azure Event Hubs using
                                   readStream, writes to ADLS Gen2 Parquet.
                                   Checkpointing ensures exactly-once delivery.
                                   Secrets come from Key Vault — never hardcoded.

  slv_transform_transactions     — Incremental load from Bronze. Runs three
                                   data quality gates: null checks, dedup on
                                   raw_log_id, amount > 0 guard. Logs DQ
                                   metrics to a control table. Delta MERGE
                                   for idempotent upserts.

  slv_transform_auth             — Parses JSON payloads, derives country from
                                   IP, standardises auth event types. Computes
                                   per-user failure velocity using a 1-hour
                                   rolling window — flags suspicious login
                                   patterns before they become incidents.

  gld_build_fact_transactions    — Builds the star schema with a 5-way
                                   broadcast join. Applies Z-score anomaly
                                   scoring on amount and response_time_ms.
                                   Normalises to a 0-1 anomaly_score.
                                   Labels each transaction: NORMAL,
                                   SUSPICIOUS, or HIGH_RISK.

  gld_build_aggregates           — Hourly transaction aggregates with P95
                                   response time. Daily auth aggregates with
                                   failure rates and unique IP counts.
                                   Dynamic partition overwrite — reruns are safe.

The AI scoring in the Gold notebook deserves a moment. We used Z-score
rather than a black-box model for a reason: it's explainable. A compliance
officer can look at an anomaly_score of 0.94 and understand it means the
transaction amount was 4.7 standard deviations from the norm for that account.
That's auditable. That matters in banking.

--------------------------------------------------------------------------------
THE PIPELINE CONVERSATION
--------------------------------------------------------------------------------

Four Synapse Pipeline JSON files to orchestrate the whole thing:

  pl_bronze_ingest          — Runs every 15 minutes. Reads the last watermark
                              from a control table so it never double-processes.
                              Wraps the notebook in error handling. Updates
                              the watermark on success, logs failure on error.

  pl_silver_transform       — Runs transactions and auth transforms in parallel
                              (no dependency between them, so why wait?).
                              After both complete, runs a zero-row validation —
                              if Silver has no data for the batch, the pipeline
                              hard-fails rather than silently producing empty Gold.

  pl_gold_build             — Builds facts, then aggregates (in sequence —
                              aggregates depend on facts). Refreshes Synapse
                              views. Notifies a Logic App webhook on success
                              and failure.

  pl_master_orchestrator    — The conductor. Runs Bronze → Silver → Gold in
                              sequence. Each stage has an Until loop with a
                              timeout so a hung job doesn't block the pipeline
                              forever. Sends a combined status summary at the end.

The watermark pattern in Bronze is worth calling out. It means the pipeline
can be safely re-run, killed mid-flight, or triggered manually without
producing duplicate data. In banking, duplicates in transaction logs are not
an inconvenience — they're a compliance problem.

--------------------------------------------------------------------------------
THE INFRASTRUCTURE CONVERSATION
--------------------------------------------------------------------------------

One Bicep file to stand up the entire Azure environment:

  Azure Synapse Workspace          — The hub. MSI-authenticated, managed
                                     virtual network, data exfiltration
                                     protection on.

  ADLS Gen2                        — ZRS redundancy, HNS enabled, shared key
                                     auth disabled, public blob access off.
                                     Four containers: bronze, silver, gold,
                                     synapsefs.

  Event Hubs                       — Standard tier, auto-inflate to 10 TUs,
                                     Avro capture to the bronze container.

  Key Vault                        — RBAC auth, 90-day soft delete, purge
                                     protection. No secrets in config files,
                                     ever.

  Synapse Spark Pool               — MemoryOptimized Small, autoscale 3-10
                                     nodes, 15-minute autopause. You only pay
                                     for what you use.

  Synapse Dedicated SQL Pool       — DW100c (parameterised — scale up for
                                     production, keep it small for dev).

  Azure OpenAI                     — Placeholder wired in for the LLM
                                     summarisation use case. Model deployments
                                     are a separate management step.

  Role Assignments                 — Synapse MSI gets Storage Blob Data
                                     Contributor on the storage account and
                                     Key Vault Secrets User on the vault.
                                     Least privilege from the start.

No hardcoded secrets. No hardcoded resource names. Everything parameterised
by environment (dev / test / prod) and prefix.

--------------------------------------------------------------------------------
THE ER DIAGRAM CONVERSATION
--------------------------------------------------------------------------------

Finally, we documented the whole data model properly — because a platform
nobody understands is a platform nobody trusts.

The ER document gives you:

  - Three Mermaid diagrams you can paste into any GitHub markdown file,
    Confluence page, or draw.io and get a rendered entity-relationship diagram

  - A full FK relationship matrix — every foreign key in the system,
    source column, target column, cardinality, and a note on why it exists

  - Star schema diagrams for each Gold mart — so any analyst can see at a
    glance which dimensions surround which fact table

  - SCD2 mechanics with a worked example — what happens when a customer's
    risk rating changes from LOW to HIGH mid-year, and how a query in December
    can correctly see what it was in March

  - Data lineage — follow any Gold table back through Silver, back through
    Bronze, all the way to the source system that generated the original log

  - The naming convention reference — so the next engineer who joins the team
    immediately understands that _sk means surrogate key, ai_ means
    AI-generated column, and brz_ means don't touch without a very good reason
